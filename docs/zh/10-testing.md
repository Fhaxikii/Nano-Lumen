# 10 · 测试

**这篇讲什么**：如何运行测试、测试的组织方式、以及如何新增一个测试。
**读完你能做什么**：在提交改动前完成验证，并为新功能补上测试。
**前置**：`01-getting-started.md`。

## 运行全部测试

```
bash run_tests.sh
```

期望输出：

```
OK 真·全量 0 失败
```

任何其他输出都表示有失败项，脚本会逐条列出失败的文件与汇总行。

## 运行单个测试

```
python tests/t_xxx.py
```

测试文件可以独立运行，不依赖测试框架。

## 组织方式

测试全部位于 `tests/`，文件名以 `t_` 开头。每个文件对应一个功能领域，
独立运行，不共享状态。

测试不使用 pytest 或其他框架，而是普通脚本：定义一个 `check()` 函数
收集断言结果，末尾打印 `通过数/总数 通过`。

`run_tests.sh` 通过解析这一行汇总来判定成败。它同时接受两种汇总格式，
并且会检查通过数是否等于总数——只检查"失败数为 0"会放过
"77/79 通过"这种情况。

## 新增一个测试

1. 在 `tests/` 下新建 `t_<领域>.py`。
2. 参照现有测试的形状：定义 `check(ok, name, note)`，逐条断言，
   末尾打印汇总行。
3. 汇总行格式必须能被 `run_tests.sh` 识别，否则会被判为"无汇总"而失败。
4. 测试应当能独立运行，不依赖其他测试先跑过。

## 测试写什么

优先钉住那些"失效时不会报错"的性质。这类缺陷不会抛异常，
只会安静地做错事，靠人工验收很难稳定发现。例如：

- 某个数据的写入是否只有一个入口。
- 某个顺序约束是否成立。
- 某个降级路径是否真的被走到。

一条断言只保护它写下的那个性质。如果一个函数有两条约束，
只钉住其中一条，另一条仍然可能被破坏。

## 已知的失败项

`tests/t_f5_live.py` 在内存不足时会以返回码 139 崩溃。
它加载嵌入模型，而该模型需要一次性提交约 2.3 GB。
这是环境问题，不是代码缺陷。判断方式：其余测试全部通过，
且系统可用内存低于该值。

---

## 怎么验证你改对了

1. 新增的测试单独运行时通过。
2. 故意破坏被测的性质，确认测试会失败——一个从不失败的测试没有意义。
3. `bash run_tests.sh` 输出 `OK 真·全量 0 失败`。
