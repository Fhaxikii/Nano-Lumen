# 03 · 配置

## 配置分布

配置分散在三处，划分依据是"这份数据跟着谁走"：

| 位置 | 内容 | 跟着谁走 |
|---|---|---|
| `.env` | 密钥、接口地址、代理 | 用户与机器 |
| `config/` | 行为规则、人格、系统指令 | 版本 |
| `data/` | 运行期状态与用户选择 | 用户 |

这个划分有实际后果：升级版本时 `config/` 会被覆盖，`data/` 与 `.env` 不应被覆盖。

## `.env`

项目根目录，不进版本控制。

这里的每一项都可以在界面上填写（设置 → 通用 → 环境配置），
界面保存后直接写回这个文件，两边是同一份数据。手工编辑同样有效。

| 键 | 说明 | 界面可填 |
|---|---|---|
| `NANO_API_VENDOR` | 模型厂商标识，取值范围见 `core/models.py` 的 `vendors()` | 是 |
| `NANO_API_RELAY_API_KEY` | API 密钥。名称中的 RELAY 是历史遗留，无论是否使用中转都存这里 | 是 |
| `NANO_API_RELAY_BASE_URL` | 中转地址。留空则使用所选厂商的官方地址 | 是 |
| `HTTP_PROXY` / `HTTPS_PROXY` | HTTP 代理。界面上填一次会同时写入两者 | 是 |
| `HF_HUB_OFFLINE` | 本地检索模型是否离线加载。由 `_setup_rag_models.py` 在下载成功后写入 | 否 |

### 关于 `HF_HUB_OFFLINE`

不要手工提前添加这一项。模型缓存尚未存在时把它设为 `1`，加载会直接进入离线模式，
于是模型永远下载不下来。正确的写入时机是下载成功之后，由 `_setup_rag_models.py` 自己完成。

反过来，下载完成后如果它没有被设上，也存在风险：加载时会联网重新拉取，
中途被打断会改写本地缓存的引用并写入否定缓存，
结果是权重文件仍在磁盘上却再也无法加载。相关记录见 `core/rag.py` 顶部。

`HF_ENDPOINT`（模型下载镜像）由 `install.ps1` 设置为用户级环境变量，不写入 `.env`。

### 逃生阀

以下键不出现在默认的 `.env` 中，也没有对应的界面控件。
它们用于覆盖默认行为，仅在确有需要时手工添加：

| 键 | 说明 |
|---|---|
| `NANO_MODEL` | 强制指定主模型，绕过界面上的选择 |
| `NANO_RELAY_DEFAULT_MODEL` | 强制指定默认模型 |
| `NANO_ENABLE_CLAUDE_THINKING` | 设为 `0` 时不发送思考参数 |
| `NANO_THINKING_BUDGET` | 思考预算上限，仅对需要显式预算的模型有效 |
| `TESSERACT_CMD` | OCR 可执行文件路径。未设置时按 PATH 与默认安装位置查找 |

`ANTHROPIC_API_KEY` 已废弃。旧版本按"是否填写中转地址"决定密钥存哪个键，
现已统一到 `NANO_API_RELAY_API_KEY`。代码中保留读取仅为兼容旧配置，不要新写入。

### 清除一个键

通过界面清空某一项时，对应的行会被整行删除，而不是注释掉。
把值保留在注释里意味着界面显示为空而文件中仍然存在，
在打包或分发时会被一并带出。

## `config/`

| 文件 | 内容 |
|---|---|
| `os_config.json` | 桌面自动化的风险升级规则、限额与自检参数 |
| `mcp_servers.json` | MCP server 列表 |
| `persona.txt` | 人格设定 |
| `system_instruction.txt` | 系统指令 |

`os_config.json` 中的风险升级规则是数据而非代码，用户可以增补。
规则的匹配与合并逻辑见 `core/os_layer/dsl.py`，规则表本身不硬编码。

## `data/`

运行期产生，不应手工编辑，也不应提交到版本控制。

| 文件 | 内容 |
|---|---|
| `model_config.json` | 厂商与模型的事实表 |
| `throttle_config.json` | 用户在界面上做出的选择 |
| `usage.json` / `usage_config.json` | 用量统计与限额设置 |
| `user_profile.json` | 用户个人信息 |
| `indexed_hashes.json` | 知识库入库记录，用于增量索引 |
| `parse_reports.json` | 文件解析结果 |
| `os_state.json` | 桌面自动化的六个权限开关与 auto 模式 |
| `context_last_known.json` | 上下文状态快照 |
| `memory_water.json` | 记忆水位 |
| `proactive_affect.json` / `proactive_ledger.json` | 主动行为的状态与记录 |
| `breadcrumbs.json` | 会话轨迹 |
| `models_cache.json` | 厂商接口返回的模型列表缓存 |

`data/` 下还有若干目录：`knowledge/` 存放知识库文件，`chat_images/` 存放
对话中出现过的图片，均为内容寻址。

### 两张表分开的原因

`model_config.json` 记录的是厂商事实：某个厂商有哪些模型、每个模型支持什么。
它跟随版本更新。

`throttle_config.json` 记录的是用户选择：主模型选了哪个、各角色分派了哪个、
计数器显示哪一档。它跟随用户。

把两者混在一起会导致升级时要么丢掉用户选择，要么无法更新厂商事实。

同一条判据也适用于桌面自动化：`config/os_config.json` 存版本事实（风险升级规则、
限额、自检参数），`data/os_state.json` 存用户状态（六个权限开关与 auto 模式）。

这一处的后果比模型表更重。权限开关如果留在 `config/` 里，它会跟着版本一起被分发——
把一台用过的机器上拨开的开关（包括高危操作总闸）发给新用户，
等于新用户一装上所有闸门就是开的。落盘位置由 `core/os_layer/dsl.py` 的
`os_state_path()` 单点决定，读写两侧都走它。

## 新增一个配置项

1. 判断它跟着谁走，据此决定放 `.env`、`config/` 还是 `data/`。
2. 读取时提供默认值，配置缺失不应导致启动失败。
3. 如果它需要出现在界面上，在 `app.py` 的设置面板中添加控件，
   并确保保存后立即生效，不要求重启。
4. 如果同一份数据在多处被读取或写入，收敛到一个函数，
   由所有入口共同调用。多个写入口只要有一个不遵守规则，规则就形同虚设。

## 怎么验证你改对了

1. 删除该配置项后启动，应使用默认值且不报错。
2. 通过界面修改后，对应行为立即改变，不需要重启。
3. 重启后设置仍然保留。
4. 运行 `bash run_tests.sh`。
