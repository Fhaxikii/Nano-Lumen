## 这一层管什么

对话越长，每一轮发送的内容越多，成本与延迟同步上升，最终撞上上下文窗口。
本层的总原则有两条，其余一切设计都从这里推出来：

- **权威与投影分离**：事实只有一份，其余全是可重建的投影。
- **遗忘不等于删除**：降级只是"不再自动想起"，原文与语义记忆都还在。

## 三本账（权威顺序写死）

| 账 | 在哪 | 记什么 |
|---|---|---|
| 对话原文 | SQLite `conversation_messages` | 历史事实的唯一权威——用户真正说过什么 |
| 衰减账本 | `core/context/decay_store.py`（`exchange_decay` 表） | 这段历史现在处于 L 几、派生出了什么 |
| 内存投影 | `memory/manager.py` 的 `storage` | 真正发给模型的临时形态，随时可重建 |

不一致时**对话原文永远最高**：宁可重新花一次提炼费用，也不拿过期摘要当事实。
来源hash、内容校验都必须算在**落盘账本**上——投影按定义就会变，拿它当基准
等于给自己造一个永远对不上的比较。详见 [07a](07a-memory-data.md)。

## 单位：一次交换（Exchange）

阶梯压缩的最小单位是"一次交换"（用户发言 → Nano 回复收尾），不是一个 Task：
Task 跨多轮且懒创建，简单问答根本没有 Task，按 Task 归属会让那类交换整批绕过压缩。
它在 `core/context/exchange.py` 里是**纯函数 + 只读视图**——只是"怎么看这堆消息"的
分组规则，没有自己的存储。

## 五箭头流水线

每轮对话结束后（`finally` 里，此时当前交换已经 closed），若总开关
`_settings.ladder_enabled` 为真，编排层依次执行（`core/orchestrator.py` 搜索
`run_l0_to_l1` 可定位）：

```
L0→L1  纯改写，不调用模型（免费档，永远先做）
L1→L2  过提炼器生成结论行（付费，刻意排在免费档之后）
L2→L3  交接语义记忆并验证可召回（唯一用户有感的箭头）
L3→L4  索引条目过期（不删语义记忆）
──────
rebuild_projection  按权威账本重建投影（与重启水合是同一个函数）
通知 UI  聊天区与模型看到同一件事
```

逐箭头的触发条件、代价与红线见 [07b](07b-decay-ladder.md)。

## 图片不走阶梯

图片走独立路径：落盘在 `data/chat_images/`，按内容哈希寻址；对话中只保留
引用与文字说明。存入的唯一入口是 `memory/manager.py` 的 `attach_user_images`，
它同时负责登记引用——绕过它会导致图片进了对话却无法被重新查看。

## 三条铁律

改这一层之前先背下来，多数缺陷不报错，只表现为"某东西悄悄不见了"或"重复花钱"：

1. **校验和算在落盘账本上**，不算在内存投影上。
2. **只降 closed exchange**，进行中的那一轮永远 L0。
3. **遗忘 = 不再自动想起**，不删语义记忆。
