# 07 · 记忆与上下文

**这篇讲什么**：对话历史如何存储、如何随长度增长被逐层压缩、以及如何被召回。  
**读完你能做什么**：定位与上下文膨胀、记忆丢失相关的问题，或修改压缩策略。  
**前置**：[02-architecture.md](02-architecture.md)。  

> 语言：中文 · [English](../en/07-memory-and-context.md)

---

## 问题是什么

对话越长，每一轮送给模型的内容越多，成本与延迟同步上升，
最终会撞上模型的上下文窗口上限。

本项目的做法是：越旧的内容压得越狠，但不直接丢弃，
而是逐级提炼成更短的形式，并保留取回原文的途径。

## 三本账

理解这一层的前提是分清三份数据，它们的权威顺序是固定的：

| 数据 | 位置 | 角色 |
|---|---|---|
| 对话原文 | SQLite | 历史事实的唯一权威，用户实际说过什么 |
| 衰减账本 | `core/context/decay_store.py` | 记录每段对话当前处于哪一层 |
| 内存投影 | `memory/manager.py` 的 `storage` | 临时形态，随时可从上面两份重建 |

不一致时以对话原文为准。宁可重新支付一次提炼开销，
也不要拿一份过期的摘要当作事实。

内存投影与落盘数据是故意不同的：内存中图片会被替换为占位符，
重启后又会按记录重新算出说明。因此涉及"内容有没有变"的校验
必须基于落盘的原文计算，基于投影计算会导致每次重启都判定为内容已变，
从而无限重复提炼。

## 分层

层级用 L0 到 L4 表示，写作字符串而非数字，便于在日志与数据库中直接阅读，
并且将来增加一层不会改变已有数据的含义。

| 层 | 含义 |
|---|---|
| L0 | 原文。当前这一轮永远是 L0 |
| L1 | 老化。内容仍在，但不再以完整形态每轮携带 |
| L2 | 结论行。经模型提炼后的结构化结果 |
| L3 | 交接给语义记忆，并验证确实能取回 |
| L4 | 仅保留索引 |

只有已经结束的对话回合会被降级，进行中的那一轮不会。

层与层之间的代价差别很大：L0 到 L1 是纯改写，不调用模型；
L1 到 L2 每一次都是一次模型调用，因此单独设有上限。

## 模块划分

| 文件 | 职责 |
|---|---|
| `core/context/meter.py` | 计量：当前上下文有多厚 |
| `core/context/budget.py` | 预算：离水位还有多远 |
| `core/context/exchange.py` | 定义"一次交换"，即分层的最小单位 |
| `core/context/decay_store.py` | 衰减账本 |
| `core/context/decay.py` | 执行降级 |
| `core/context/digest.py` | 结论行的结构定义与提炼契约 |
| `core/context/bridge.py` | 把结论行交接给语义记忆 |
| `core/context/guard.py` | 硬窗口守卫 |

`guard.py` 是确定性兜底：前面几层都是启发式的，可能失效，
而它在接近上限时直接拦截，不依赖判断。

## 语义记忆

`core/semantic_memory.py` 与 `core/memory_index.py` 负责跨会话的长期记忆。
被降到 L3 的结论行会交接到这里，并且交接时会验证确实能取回来，
不做"写进去就当成功"的假设。

## 图片

图片不进入分层压缩，走独立路径：
落盘存储在 `data/chat_images/`，按内容寻址，文件名是内容哈希。
对话中只保留引用与文字说明，需要重看时按引用取回原图。

存入的唯一入口是 `memory/manager.py` 的 `attach_user_images`，
它同时负责登记引用。绕过它的路径会导致图片虽然进入了对话，
却无法在后续轮次中被重新查看。

## 修改注意

这一层的多数缺陷不表现为报错，而表现为"某个东西悄悄不见了"或
"重复花钱"。因此改动时优先确认：

- 校验和算在权威数据上，不是算在投影上。
- 降级只作用于已结束的回合。
- 每一条通往落盘的路径都经过同一个入口。

## 怎么验证你改对了

1. 进行一次长对话，观察监控抽屉中的上下文占用随分层生效而下降。
2. 重启后确认分层状态被正确恢复，没有整体退回原文。
3. 询问一件只在早期对话中出现过的事实，确认仍能答对。
4. 确认没有出现重复提炼：日志中同一段对话不应反复触发模型调用。
5. 运行 `bash run_tests.sh`。
