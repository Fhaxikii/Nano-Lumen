## 先读这一节：我们不接受什么

提前说明比事后拒绝好。一个已经写完的 PR 被拒，对提交者是白做，
对维护者是既要花时间 review 又要拒绝。

### 明确不接受

**改动核心安全闸**
指桌面自动化的风险计算、权限开关、以及自动模式下的危险命令判定。
这些机制的失效后果是用户的机器被执行了不该执行的操作。
如果你认为某处判定有误，请提 issue 说明具体场景，不要直接改。

**引入付费依赖**
任何需要付费才能使用的库、服务或模型。

**需要注册账号的服务**
包括需要 API key 的服务。用户模型厂商的密钥是唯一例外，
那是使用本项目的前提。

这三条同样适用于内置的 MCP server：免费、免注册、免密钥是硬性条件。

### 这份清单不全

它会随着实际遇到的情况增补。如果你的改动不在清单里但你不确定，
先提 issue 问一句，比写完再讨论便宜。

## 提交之前

### 1. 确认改动范围

一个 PR 只做一件事。把不相关的修改分开提交，包括顺手做的格式调整。

### 2. 跑测试

```
bash run_tests.sh
```

必须输出 `OK 真·全量 0 失败`。已知的环境相关失败项见 [10-testing.md](10-testing.md)。

### 3. 补测试

如果改动引入了新行为，补一个测试。判断标准见 [10-testing.md](10-testing.md)
的"测试写什么"一节。

### 4. 自检清单

- [ ] 没有硬编码模型名。模型通过 `core/models.py` 的相应函数解析。
- [ ] 没有硬编码颜色或字号。使用 CSS 变量。
- [ ] 涉及模型可见的文本用英文，用户可见的文本跟随用户语言。
- [ ] 新增的配置项有默认值，缺失时不导致启动失败。
- [ ] 如果修改了某个数据的写入路径，确认所有写入口都经过同一个函数。
- [ ] 如果改动会影响某个常驻界面元素，确认它会被刷新。
- [ ] 没有在界面元素创建之前加入耗时的阻塞调用。

## 读注释时会遇到的几个约定

本项目的注释密度很高，且大多解释「为什么这样做」。读的时候会碰到三类可能让人困惑的东西：

**`koala`** —— 指项目作者。注释里的「koala 定」「koala 实测撞到」意思是
这个决定或这个发现来自作者本人，不是引用某份外部资料。

**`内部设计文档`** —— 开发期的规划与决策文档，**不随仓库发行**。
引用它的地方，结论本身都写在注释里了，你不需要去找那份文档；
它出现在那里只是说明这句话的出处。

**方括号里的代号，如 `[L5]` `[F4]` `[D13]`** —— 内部推进项的编号，
同样指向不发行的文档。它们是标签，不影响你读懂那段注释在说什么。
📌 这三样都不构成理解代码的前提。看到它们时，读它们后面那句话就够了。

## 代码风格

- 遵循所改文件的既有风格：命名方式、注释密度、缩进惯例。
- 注释解释"为什么这样做"，不解释"这行代码做了什么"。
- 用户可以在界面上查看技能源码，因此 `skills/` 下的文件
  只保留接口说明，不写开发过程记录。

## 提交信息

说明改了什么、为什么改。如果修复的是一个缺陷，
描述该缺陷的表现，而不只是引用 issue 编号。

## 文档

如果改动改变了某个模块的用法，同步更新 `docs/` 中对应的那一篇。
一段描述已经不存在的机制的文字，比没有这段文字更糟糕，
因为读者会照着它做，而错误不会立即暴露。

## 怎么验证你改对了

1. `bash run_tests.sh` 通过。
2. 自检清单逐项确认。
3. 在干净的环境中重新走一遍 [01-getting-started.md](01-getting-started.md)，确认改动没有破坏首次启动。
4. 如果改动涉及界面，在两套主题下分别确认。
