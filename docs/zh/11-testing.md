## 运行全部测试

```
bash run_tests.sh
```

期望输出：

```
OK 真·全量 0 失败
```

任何其他输出都表示有失败项，脚本会逐条列出失败的文件与汇总行。

## 运行单个测试

```
python tests/cases/t_xxx.py
```

测试文件可以独立运行，不依赖测试框架。

## 组织方式

测试用例全部位于 `tests/cases/`，文件名以 `t_` 开头。每个文件对应一个功能领域，
独立运行，不共享状态。

测试不使用 pytest 或其他框架，而是普通脚本：定义一个 `check()` 函数
收集断言结果，末尾打印 `通过数/总数 通过`。

不引入框架是刻意的：跑测试不应新增依赖；且崩溃恢复类用例需要 spawn
子进程并在真实转移点 `os._exit`，裸脚本比绕开框架的输出捕获更直接。

`tests/` 根目录只放运行器 `run_all.py` 与辅助模块（`_console.py`、`_sandbox.py`、`_src.py`、`_win_window.py`），不是测试；
`_console.py` 负责控制台输出保护（见下一节第 2 步）。

`run_tests.sh` 通过解析这一行汇总来判定成败。它同时接受两种汇总格式，
并且会检查通过数是否等于总数——只检查"失败数为 0"会放过
"77/79 通过"这种情况。

## 新增一个测试

1. 在 `tests/cases/` 下新建 `t_<领域>.py`。命名只要求 `t_` 前缀；
   这个测试验证什么，写在文件的头部 docstring 里。
2. 第一行 `import tests._console`。Windows 的 cmd 默认是 GBK 编码，
   断言名里的 emoji / 特殊符号会让 `print` 抛 `UnicodeEncodeError`——
   用例被中止，而断言根本没进计数。它看起来像"跑了一半崩了"，
   实际是"断言从未存在"。`_console.py` 把编不出的字符替换为 `?`，
   保证最坏情况仍可读。断言名本身也请用控制台编得出的字符。
3. 参照现有测试的形状：定义 `check(ok, name, note)`，逐条断言，
   末尾打印汇总行。
4. 汇总行格式必须能被 `run_tests.sh` 识别，否则会被判为"无汇总"而失败。
5. 测试应当能独立运行，不依赖其他测试先跑过。

## 测试写什么

优先钉住那些"失效时不会报错"的性质。这类缺陷不会抛异常，
只会安静地做错事，靠人工验收很难稳定发现。例如：

- 某个数据的写入是否只有一个入口。
- 某个顺序约束是否成立。
- 某个降级路径是否真的被走到。

一条断言只保护它写下的那个性质。如果一个函数有两条约束，
只钉住其中一条，另一条仍然可能被破坏。

三条来自实战的纪律：

- **故障注入，确定性优先于真实性。** 目的是验管道通不通，不是复现真实错误。
- **"期望某件事没发生"的用例，必须同时断言"前置条件确实发生过"。**
  否则注入失效会伪装成通过——比如子进程死在建库、根本没到注入点，
  而用例期望恰好是"什么都没持久化"，于是假通过。
  把子进程退出码纳入断言，不符时打印它的 stderr 尾部。
- **检查"某个标识符已删干净"必须用 `ast.walk`，不要 `in src`。**
  文本匹配会被注释和 docstring 误中——源码里把"为什么删它"解释得越认真，
  误中概率越高。同时补一个前置断言：让 AST 在同一棵树里找一个确定
  还存在的名字，证明分析器真的在工作。

## 已知的失败项

`tests/cases/t_f5_live.py` 在内存不足时会以返回码 139 崩溃。
它加载嵌入模型，而该模型需要一次性提交约 2.3 GB。
这是环境问题，不是代码缺陷。判断方式：其余测试全部通过，
且系统可用内存低于该值。

## 怎么验证你改对了

1. 新增的测试单独运行时通过。
2. 故意破坏被测的性质，确认测试会失败——一个从不失败的测试没有意义。
3. `bash run_tests.sh` 输出 `OK 真·全量 0 失败`。
