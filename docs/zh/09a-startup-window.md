# 09a · 启动、窗口与主题

**这篇讲什么**：进程如何从冷启动走到可用窗口——托盘常驻、原生窗口、同步初始化时序、mini 窗与被动挂起的绑定、主题机制、SkillWatcher。  
**读完你能做什么**：安全地改启动顺序、窗口行为、主题切换或技能热重载，不引入"启动期写 UI"类静默失败。

## 启动顺序（一条不许乱的链）

```
进程启动
→ CrashJournal 异常钩子安装（日志可见 "breadcrumb 为主，钩子为辅"）
→ Runtime Kernel 就绪（47 个命令 · nano_runtime.db）
→ reconciler 启动恢复（崩溃遗留任务的"要不要继续"在这里问）
→ 技能装载（registry，六个官方技能）
→ WebUI() 构造
→ 【同步初始化】(:16687 一带)   ⚠️ 必须在 ui.run() 之前同步跑，不能挂 ui.timer
→ ui.run() 
→ WebView2 原生窗口
→ _on_browser_connect（客户端连接，重贴主题；对话状态保持不变）
```

**已知时序坑（务必记住）**：

1. **RAG 初始化线程**（普通 `threading.Thread`）在 WebUI 构造时启动，早于
   `ui.run()`——它是"后台线程写 UI 必须显式进 client 上下文"这条规则最典型
   的受害场景（app.py 注释）。
2. **上一个进程留下的清理必须在 `ui.run()` 之前同步做**（:16687 注释原文：
   不能挂 ui.timer）——异步化它 = 用户可能在清理完成前就开始操作。
3. **恢复类提示（arm_restart_notice）在 WebUI 之前挂好**——重启提示依赖
   runtime 身份（`rt_*`），晚了会丢。

## 托盘与"关闭不退出"

- 系统托盘（pystray，:261 一带）：**点关闭是藏到托盘，不是退出**——
  这是"常驻"在用户可感层面的实现（Changelog v1.11 起）。
- 真正的退出走托盘菜单 → `_quit`。改窗口关闭行为的 PR 若让"关闭 = 退出"，
  等于推翻常驻定位，不会通过。

## 原生窗口层

- pywebview + WebView2 渲染；`nano_set_min_size`（等窗口 API 走
  兼容层封装。

## mini 窗与被动挂起（三合一绑定）

⭐ **mini 窗开 = GUI 模式 = 被动挂起全量监控，三者绑定**（:5333 / :5370）：

- mini 窗开 → 进入 GUI 模式 → Nano 的被动挂起开始监控（用户在别的窗口
  打字时 Nano 收敛行为）。
- mini 窗关 → 退出 GUI 模式 → 停止监控。

改任何一个分支，另外两个语义都要同步检查——它们是同一个"用户正在别的
地方工作"状态的三种表现，拆开就会出现"窗开着但监控没跑"这类半激活态。

## 主题

- `_apply_theme_visuals`（是统一入口；明暗切换后**重贴当前
  视图**（客户端重连时也是重贴主题、对话状态不动，见 `_on_browser_connect`）。
- 样式大量使用 CSS 变量（`var(--nano-fg)` 等）——新组件用它而不是写死颜色，
  主题切换才能自动跟随。

## SkillWatcher（

技能文件监听（watchdog），实现技能热重载的"检测"半边；重载动作在
`core/registry.py` 的 `reload_all`（见 [04-writing-a-skill.md](04-writing-a-skill.md)）。
注意它跑在 watcher 线程——往 UI 反馈（如技能列表刷新）同样要过 client 上下文。

## 改动手把手

**场景 A：往启动链里加初始化**
1. 先问三连：它必须同步吗（用户可能在它完成前操作）？它写 UI 吗（哪个
   线程、client 建立了吗）？它依赖 runtime/kernel 吗（谁先谁后）？
2. 同步且无 UI 依赖 → 放 `ui.run()` 之前的同步初始化段。
3. 异步/重 UI → 挂 `ui.timer` 或客户端连接回调之后。

**场景 B：改窗口行为**
区分"藏到托盘"与"退出"两条路径；关闭语义保持常驻。DPI 相关改动必须
配套验证视觉定位（06b 的坐标一致性）。

**场景 C：加/改主题变量**
在 `_apply_theme_visuals` 定义变量，组件里消费；明暗两套各验证一遍
（含工具卡、代码块等易漏角落）。

## 怎么验证你改对了

1. `bash run_tests.sh`（启动相关：`t_f1_stage7_bgjob.py`、`t_replay_chat_events.py`）。
2. 冷启动（无历史）+ 热启动（有历史且上次非正常退出）各一次：
   热启动应看到"要不要继续"的恢复询问。
3. 启动期日志顺序核对：CrashJournal → Kernel → reconciler → 技能 →
   ui.run（顺序乱了通常不是报错，是行为怪）。
4. mini 窗开合一轮：监控启停与窗口形态三态一致。
